# E-Commerce Order Analytics System

An end-to-end data analytics project that generates realistic (intentionally messy)
e-commerce data, cleans it, loads it into a SQL database with proper constraints, and
answers business questions using SQL — from basic aggregations to window functions,
CTEs, cohort analysis, and RFM customer segmentation. A command-line tool ties it
together into on-demand business reports.

## Skills demonstrated
Python (Faker, pandas), SQL (SQLite — joins, subqueries, CTEs, window functions),
data cleaning (pandas DataFrames, deduplication), referential integrity validation,
CLI tool design (argparse, tabulate), edge-case testing (including CLI-level tests
via subprocess).

## How to Run (from scratch)

```bash
# 1. Install dependencies
pip install pandas faker tabulate

# 2. Generate the raw datasets (500+ rows each, with intentional messiness)
#    writes to data/Raw/
python Scripts/data_generator.py

# 3. Clean the data and validate referential integrity
#    reads from data/Raw/, writes to data/cleaned/
python Scripts/clean_data.py

# 4. Create the schema (PK/FK/NOT NULL/CHECK constraints) and load cleaned data into SQLite
python load_to_sqlite.py

# 5. Run the edge-case test suite
python test_edge_cases.py

# 6. Generate a report from the command line
python Scripts/report_cli.py --report revenue
python Scripts/report_cli.py --report top_customers --limit 10
python Scripts/report_cli.py --report retention
python Scripts/report_cli.py --report segmentation

# 7. (Optional) Explore all 21 SQL queries interactively
jupyter notebook analysis.ipynb
```

## Data Model

| Table | Key columns | Notes |
|---|---|---|
| `customers` | `customer_id` PK | `customer_type`: REGULAR / PREMIUM / VIP |
| `products` | `product_id` PK | `category`: Electronics, Clothing, Home, Books |
| `orders` | `order_id` PK, `customer_id` FK | `customer_id` nullable (~5% missing on purpose); `status`: PLACED/SHIPPED/DELIVERED/CANCELLED/RETURNED |
| `order_items` | `item_id` PK, `order_id` FK, `product_id` FK | negative `quantity` (~3%) represents a return |

Constraints (PK, FK, NOT NULL, CHECK) are defined in `sql/schema.sql` and applied by
`load_to_sqlite.py` before any data is inserted.

## Intentional Data Issues (and how they're handled)

| Issue | Introduced in | Fixed/handled in |
|---|---|---|
| ~5% missing `customer_id` | `data_generator.py` | `clean_orders()` — flagged as NULL, kept (not dropped) |
| ~10% wrong date format (`DD-MM-YYYY`) | `data_generator.py` | `clean_orders()` — reparsed into `YYYY-MM-DD HH:MM:SS` |
| ~15% messy product names (extra spaces / mixed case) | `data_generator.py` | `clean_products()` — trimmed + title-cased |
| ~2% invalid emails (no `@`/domain) | `data_generator.py` | `validate_emails()` — regex-flagged, reported (not silently dropped) |
| ~3% negative quantity (returns) | `data_generator.py` | kept intentionally — used in return-rate analysis (Query 6) |
| ~2% duplicate rows in `customers` and `orders` (exact-copy rows, same ID) | `data_generator.py` | `dedupe_customers()` / `dedupe_orders()` — dropped, kept first occurrence |
| Referential integrity | n/a | `check_referential_integrity()` confirms every `order_id` in `order_items` exists in `orders` |

`clean_data.py` loads every CSV into a `pandas.DataFrame`, does all cleaning/dedup/validation
as DataFrame operations, and writes a full summary to `data/cleaned/cleaning_report.txt` every run.

## SQL Analysis — 21 Queries

**Basic joins & aggregations** (`sql/aggregations.sql`)
1. Total revenue per category
2. Top 10 customers by order value
3. Month-wise order count (last 12 months)
4. Customers who never had a delivered order
5. Products with more returns than purchases
6. Return rate per category
0. Average Order Value (AOV) by customer type (REGULAR/PREMIUM/VIP)

**Window functions & CTEs** (`sql/window_functions.sql`)
7. Running total of revenue per region (`SUM() OVER`)
8. Product ranking per category (`DENSE_RANK()`)
9. Days between consecutive orders (`LAG()`), "At Risk" flag
10. Multi-level CTE — monthly revenue → High/Medium/Low category → customer counts
11. Customer quartiles by lifetime value (`NTILE(4)`)
12. Year-over-year revenue comparison
13. First vs most recent purchase category (`FIRST_VALUE()`)
14. Cumulative revenue distribution (% from top customers)

**Cohort & retention** (`sql/cohort_analysis.sql`)
15. Cohort retention by registration month (month 0–3)
16. Frequently-bought-together product pairs (self-join)

**Customer segmentation** (`sql/segmentation.sql`)
17. Frequency segmentation (One-time / Occasional / Loyal)
18. Spend-tier segmentation (Low / Medium / High)
19. AOV by frequency segment
20. RFM analysis — Recency, Frequency, Monetary, each scored 1–5 via `NTILE`, combined into Champion/Loyal/At Risk/Lost
21. Churned vs Repeat customers (churn = 60+ days since last order)

All 21 queries are also runnable interactively with saved outputs in `analysis.ipynb`.

## CLI Reporting Tool

```bash
python Scripts/report_cli.py --report {revenue|top_customers|retention|segmentation} [--limit N]
```
Connects to `ecommerce.db` and prints the selected report as a formatted table (via `tabulate`):

- `revenue` — total revenue per product category
- `top_customers` — top N customers by total order value (`--limit`, default 10)
- `retention` — cohort retention rate by registration month, months 0–3
- `segmentation` — customer counts per RFM segment (Champion / Loyal / At Risk / Lost)

Bad input is handled without crashing:
- an unknown `--report` value is rejected by `argparse` with a usage message
- a non-positive `--limit` is rejected before any query runs
- a missing `ecommerce.db` prints a clear message instead of an unhandled exception

Sample outputs are saved in `output/sample_reports/`.

## Edge Case Handling

`test_edge_cases.py` verifies:
1. `order_items` referencing a non-existent `order_id` is detected via `LEFT JOIN ... WHERE ... IS NULL`
2. `discount_percent > 100` produces a negative (clearly invalid) revenue value, flagging bad data
3. `quantity = 0` computes to zero revenue without crashing
4. A future `order_date` is correctly detected as being ahead of "now"
5. `report_cli.py` fails cleanly (no traceback, message + non-zero exit) when `ecommerce.db` is missing
6. `report_cli.py` rejects an invalid `--report` value via `argparse`
7. `report_cli.py` rejects a non-positive `--limit` value

Tests 5–7 run `report_cli.py` as a real subprocess rather than re-implementing its logic,
so they catch things a pure logic test would miss (e.g. argument parsing, exit codes).

## Known limitations / notes

- Dataset spans ~13 months, so year-over-year comparisons (Query 12) mostly show `NULL`
  for the earliest months (no prior-year data exists yet) — this is expected, not a bug.
- Product/category names are generated via Faker's random word generator, so names like
  "Significant Academic" are cosmetic placeholders, not meaningful product names.
- `order_items` doesn't get duplicate rows injected (only `customers` and `orders` do) since
  `item_id` is generated uniquely per row and duplicating it would just be a second copy of
  the same order/product pairing, which doesn't add a meaningfully different data-quality issue.
